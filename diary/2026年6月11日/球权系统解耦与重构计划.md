# 球权系统解耦与重构计划

> 制定日期：2026-06-11
> 配套文档：`球权系统设计落地可行性核查.md`（本目录）
> 设计来源：`diary/2026年6月9日/持球设计文档/`
> 目标代码库：`E:\scrum`
> 目的：在落地三态球权系统的**同时**，对沿途强耦合代码做"附带解耦"，让球权链路从"判定/门控/消费三件事缠在一起"演进为"分层、可替换、可灰度"的结构，降低后续迭代成本

---

## 零、指导原则

1. **机会主义重构（童子军原则）**：只解耦本次实现必然路过的代码，不为解耦而解耦，不扩大改动面。每碰一处，离开时比来时干净一点。
2. **先立边界，再填逻辑**：每层先抽出稳定的抽象接口（边界），新球权逻辑只在边界内侧生长，边界外侧的调用方保持不变。
3. **抽象先行、实现搭载**：解耦不是独立工程，而是"为了让新逻辑有地方放"。每个解耦动作都直接服务于核查文档识别的某个改造点。
4. **全程可灰度**：复用真身已有的 `BALL_OWNER_MECH_SWITCH` 总开关思路，新抽象层默认走旧路径，开关开启才走新三态逻辑，保证任何一步都能回滚。
5. **不动核心算法**：预测核心（take_frame 选人、追球粗筛）保持算法不变，只重排其职责边界。

## 一、耦合现状诊断

核查文档已逐条核对存在性，这里聚焦"**耦合在哪、为什么是债**"。

| # | 耦合点 | 真身位置 | 耦合本质 | 债务表现 |
|---|---|---|---|---|
| C1 | 球权判定散落 | `BallOwnerManager.get_is_owning_ball()` 直接 `ball_owner == team_eid`（`:84`，注释"临时代码"） | 判定逻辑无封装，调用方各自比较 eid | 三态无处安放；任何判定规则变更要改多处 |
| C2 | 查询层直读黑盒 | `FakeTeam.IsOwningBall()` 同时含 `black_box.get_is_owning_ball()` 和 `black_box.ball_owner == self.eid` 两条分支（`:544-552`） | 上层直接依赖底层字段，旁路了 manager | UNOWNED 双 False 需改两条分支，灰度逻辑分叉 |
| C3 | 预测三职合一 | `TakeBallManager::_update_ball_owner()`（`take_ball_manager.cpp:333`） | 胜者判定 + 上报门控 + 防抖三件事写在一个函数里 | 改 K 帧门控会触碰胜者判定；子条件 C 无独立落点 |
| C4 | 参数语义混淆 | `SINGLE/DOUBLE_SWITCH_BALL_TIME`（`AIParamModule.json:531`） | 同一参数既当"胜者判定距离"又当"上报范围门控" | 拆 K 帧时语义无法平移，调参影响面不清 |
| C5 | Situation 无生命周期抽象 | `BaseSituation`（`base_situation.h:23`）仅 `check_exit_condition()` 纯虚 | 退出判定与"无 dribbler"硬绑：`if (dribbler==nullptr) return false` | UNOWNED 时永不退出，Role/HR 继续跑；Hold 无处挂 |
| C6 | 战术消费瞬时球权 | `tactic_task_manager.cpp:233` `m_should_enable = ...get_is_owning_ball()` | Bidding 直接吃瞬时球权，无稳定层 | 反复抢断 → 反复重竞标，抖动直达战术层 |
| C7 | 执行层二元硬映射 | `FixTeamHomeRegion` 按攻/防选 `OFF/DEF_LATTICE_INDEX` | 跑位格位只认"攻/防"二态 | 无 UNOWNED 第三态入口，无法分类处理/Stay HR |

**核心债**：球权语义在 C++ 预测层、Python 黑盒层、查询层、战术层之间**没有单一权威源**，每层各自从 `ball_owner` 这个单 eid 字段推断状态。三态系统的实现，本质上就是为这条链路**建立单一权威 + 分层边界**。

## 二、分层解耦方案

按核查文档 §5 的"自下而上"顺序，每层一个边界。下层边界稳定后再动上层，每层可独立验收。

### L1 球权状态层：建立"权威状态源"边界

**解耦目标**：让 `ball_possession_state` 成为球权的唯一权威，所有判定收口到一个方法。

- **现状（C1）**：`get_is_owning_ball()` 是裸比较，标着"临时代码"。
- **边界设计**：
  - `BallOwnerManager` 新增 `FsProperty('ball_possession_state', ...)`，表达 `OWNED_HOME / OWNED_AWAY / UNOWNED` 三态（或 `owner_eid + is_unowned` 组合，二选一，实现时定）。
  - 收口判定：`get_is_owning_ball(team_eid)` 内部改为读 `ball_possession_state`，**对外签名不变**。UNOWNED 时两队均返回 False。
  - 新增 `get_possession_state()` 暴露三态本身，供调试与上层使用。
  - `change_ball_owner()` 成为唯一写状态入口，顺带核对 `E_CHANGE_BALL_OWNER` 的 `old_team_eid` 取值时机（核查文档 §2.1 ⚠️）——把 old 值在赋新值**之前**缓存，修掉既有"传的是新值"的隐患。
- **搭载实现**：三态原语（净新增）在此落地。
- **解耦收益**：判定规则从此只有一处；删掉"临时代码"注释。
- **验收**：调试工具能看到 UNOWNED；UNOWNED 时两队 `IsOwningBall()` 双 False；开关关闭时行为与旧版逐帧一致。

### L2 查询层：合并双分支，依赖抽象不依赖字段

**解耦目标**：上层只问"我有球吗"，不关心底层用什么表达。

- **现状（C2）**：`FakeTeam.IsOwningBall()` 含 `black_box.ball_owner == self.eid` 旁路分支。
- **边界设计**：
  - 把 `ball_owner == self.eid` 旁路分支**删除**，统一走 `black_box.get_is_owning_ball(self.eid)`。Street 模式等差异下沉到 L1 manager 内部处理。
  - 保留帧内缓存 `_is_owning_ball` 与 `change_ball_owner()` 置 None 的失效机制（已是良性设计）。
  - 同步核对 `FakePlayer.IsOwningBall`、`WhiteBox.IsOwningBall`（grep 命中点）是否也直读字段，一并收口到 manager。
- **解耦收益**：查询层不再直接耦合 `ball_owner` 字段；灰度只在 L1 一处分叉。
- **验收**：三处 `IsOwningBall` 行为一致；关开关回退无差异。

### L3 预测判定层：三职拆分（核心重构）

**解耦目标**：把 `_update_ball_owner()` 从"一锅炖"拆成三个单一职责单元。

- **现状（C3/C4）**：判定 + 门控 + 防抖缠绕。
- **边界设计**（拆成三段，依次调用，不改算法）：
  1. `has_clear_winner()` —— **纯判定**。封装核查文档 §2.2 的子条件 A/B/D（双方无 taker / 势均力敌 / 单方太远），返回 winner 或"无明确胜者"。新增**子条件 C（球速阈值）**在此落地——这是真身完全没有的纯新增逻辑，需定义球速来源与单位（核查文档 §三.1）。
  2. K 帧上报门控 —— **纯输出控制**。从 `has_clear_winner` 剥离 `SINGLE/DOUBLE_SWITCH_BALL_TIME`，重定义为"上报范围门控"，并按 `take_ball_info.pass_type`（`take_ball_manager.h:70`）分化取 K 值。修掉 C4 的语义混淆。
  3. 防抖 —— 维持 `last_judge_frame` / `SWITCH_BALL_OWNER_STAY_FRAME` 逻辑，作为独立一段，后续可下沉到 L4 缓冲层。
  - 上报仍走 `black_box->py_change_ball_owner(...)` → L1 的 `change_ball_owner()`，链路不变。
- **参数解耦（C4）**：`AIParamModule.json` 中 `SINGLE/DOUBLE_SWITCH_BALL_TIME` 改语义为 K 帧门控参数（或新增 K 系列、废弃旧名），`TIME_DIFF_THRESHOLD` 留在 `has_clear_winner`，`STAY_FRAME` 拆向防抖/缓冲。`AIParamModule.meta.json` 同步。
- **解耦收益**：调 K 帧门控不再触碰胜者判定；子条件可单测；预测算法零改动。
- **验收**：Case 2 进 UNOWNED；长传 `has_clear_winner=True` 时 Task 不中断；关开关时三段合起来与旧 `_update_ball_owner` 等价。

### L4 缓冲累积 + 战术消费层：插入"稳定球权"边界

**解耦目标**：在瞬时球权与战术消费之间插一层防抖缓冲，战术层只认稳定信号。

- **现状（C6）**：`tactic_task_manager.cpp:233` 直吃瞬时 `get_is_owning_ball()`。
- **边界设计**：
  - **缓冲累积器（净新增）**：`BallOwnerManager` 新增 `ball_ownership_stable` + `prev_state` + `frames_as_them`（N 帧累积），暴露 `get_stable_possession()`。瞬时翻转需连续 N 帧才反映到 stable。
  - **重定向消费**：`tactic_task_manager.cpp:233` 的 `get_is_owning_ball()` 改为消费 `ball_ownership_stable`。这是**一行重定向**，但前提是 L4 缓冲层先建好。
  - **Situation 生命周期抽象（净新增，C5）**：`BaseSituation` 加 `is_suspended` 挂起态 + `suspend()/resume()`，并在 `tick`/Bidding **入口**拦截"无 dribbler 时强制挂起"——核查文档 §三.4 明确：单加 Hold 不够，`check_exit_condition` 的 `return false` 会让 Situation 永远活着，必须在入口拦，不能靠 exit。挂起 ≠ 销毁，恢复时不重竞标。
- **解耦收益**：抖动被缓冲层吸收，不再直达战术层；Situation 有了正式生命周期，后续新 Situation 复用挂起语义。
- **验收**：反复抢断 `ball_ownership_stable` 不翻转；短暂失球拿回不重竞标；Situation 不重复 Bidding。

### L5 执行跑位层：二元 → 三态分类处理

**解耦目标**：跑位格位选择从"攻/防二元"扩展为"攻/防/UNOWNED 三类"，并解耦"分类"与"格位映射"。

- **现状（C7）**：`FixTeamHomeRegion` 按二元攻防选 `OFF/DEF_LATTICE_INDEX`。
- **边界设计**：
  - 引入"球权情境分类"读取点（读 L1 的三态 / L4 的稳定态），在 `FixTeamHomeRegion` 内分支：OWNED → 旧逻辑；UNOWNED → 非 taker Stay HR、超时收缩、分类处理（GK 豁免出击）。
  - 把"是 taker 吗 / 是 GK 吗"等分类判定与"选哪个格位"分离，避免新分支继续堆砌 if。
- **搭载实现**：子条件 C 之外的 UNOWNED 跑位行为在此落地。
- **解耦收益**：跑位层有了三态入口，后续战术风格可在此扩展而不动球权链路。
- **验收**：Case 3/5/7 非追球人 HR 不切换；GK 豁免正常出击。

## 三、依赖顺序与边界关系

```
L1 球权状态层 (权威源)
   │  get_is_owning_ball() / get_possession_state()
   ▼
L2 查询层 (FakeTeam/FakePlayer/WhiteBox.IsOwningBall) ── 消费 L1
   ▲
L3 预测判定层 (_update_ball_owner 拆三段) ── 写 L1 (change_ball_owner)
   │
   ▼
L4 缓冲层 (ball_ownership_stable) ── 派生自 L1
   │  get_stable_possession()
   ├─► tactic_task_manager (重定向消费)
   └─► BaseSituation 挂起态
   ▼
L5 执行层 (FixTeamHomeRegion) ── 消费 L1/L4 三态
```

**关键约束**：L1 是所有层的单一权威源，必须最先稳定。L2/L3 只与 L1 交互，可并行。L4 派生自 L1，是 L5 与战术层的输入。任一层未完成，下游走旧路径（开关关闭）即可正常跑。

## 四、解耦收益（为什么值得顺手做）

| 解耦动作 | 一次性收益 | 长期复用收益 |
|---|---|---|
| L1 判定收口 | 删"临时代码"，三态有家 | 后续任何球权规则只改一处 |
| L2 删旁路分支 | 灰度逻辑不分叉 | 上层永远不直读底层字段 |
| L3 三职拆分 | 子条件可单测、K 帧独立调 | 预测层后续加判定不再"一锅炖" |
| L4 稳定层 | 抖动吸收 | 任何需要"稳定球权"的新功能直接复用 |
| L4 Situation 生命周期 | Hold 副作用根治 | 所有新 Situation 复用挂起语义 |
| L5 三态分类 | UNOWNED 跑位落地 | 跑位风格扩展不碰球权链路 |

## 五、风险与回滚

| 风险 | 来源 | 缓解 |
|---|---|---|
| 拆 `_update_ball_owner` 引入算法偏差 | C3 重构 | 拆分后保持调用次序与原函数等价；开关关闭走旧路径对拍 |
| `E_CHANGE_BALL_OWNER` old 值消费方依赖现有（错误）行为 | C1 修隐患 | 修前 grep 全部消费者，确认无人依赖"传新值"的既有行为 |
| K 帧参数语义平移调错手感 | C4 | 旧参数值先原样平移，手感调优单列阶段，不与解耦混做 |
| Situation 入口拦截位置选错仍跑 Role | C5 | 在 Bidding/tick 入口拦，不依赖 `check_exit_condition` |
| 子条件 C 球速阈值无依据 | 纯新增 | 先定来源与单位（核查文档 §三.1），无数据则该子条件可灰度关闭 |

**回滚粒度**：每层独立开关 / 复用 `BALL_OWNER_MECH_SWITCH`。任一层出问题，关该层开关回旧路径，不影响其余层。
