> 核对代码库：`E:\scrum`（Messiah 足球引擎真身）

## 一、结论概览

整体判定：**设计可落地，无硬阻塞**。底层球权链路（写入/查询/预测）与设计描述高度吻合，多数改造是"扩展/拆分/重定向"而非"推翻"。三态原语、缓冲累积器、Situation Hold 是三块净新增工作。

| 改造点 | 真身现状 | 可行性 | 性质 |
|---|---|---|---|
| `ball_possession_state` 三态 | 仅 `ball_owner` 单 eid，无三态 | ✅ 可行 | **净新增** |
| `has_clear_winner()` 抽取 | 胜者判定与上报门控耦合在 `_update_ball_owner` | ✅ 可行 | 重构拆分 |
| K 帧定点门控 | 已有 `take_frame - cur_frame` 范围门控 | ✅ 可行 | **同形替换** |
| 子条件 C（球速阈值） | `_update_ball_owner` 不查球速 | ✅ 可行 | 新增逻辑 |
| 缓冲累积器（N 帧） | 不存在 | ✅ 可行 | **净新增组件** |
| Situation Hold / `is_suspended` | `BaseSituation` 无挂起态 | ✅ 可行 | **净新增状态** |
| Situation 消费重定向 | 直接消费 `get_is_owning_ball()` | ✅ 可行 | 重定向 |
| `IsOwningBall()` UNOWNED 双 False | `ball_owner == eid`，无 UNOWNED | ✅ 可行 | 改判定源 |
| NewChaseRule 按 take_frame 选人 | **已用 `min_take_frame`** | ✅ 已满足 | 风险消解 |
| 分类处理 / Stay HR | FixTeamHomeRegion 现按二元攻防选格 | ✅ 可行 | 行为改造 |

## 二、逐条核对

### 2.1 底层写入层 —— `BallOwnerManager.py`

真身路径：`Package/Script/Python/dm33/CommonLogic/FrameSync/Components/BallOwnerManager.py`

设计描述的接口**全部存在且语义一致**：

| 设计引用 | 真身位置 | 状态 |
|---|---|---|
| `change_ball_owner()` | `BallOwnerManager.py:90` | ✅ 一致：更新 `ball_owner` → 失效缓存 → 条件广播 `E_CHANGE_BALL_OWNER` → 同步 C++ |
| `cpp_change_ball_owner()` | `:86` | ✅ C++ 提前给球权入口 |
| `record_temp_dribbler_change()` | `:69` | ✅ 含定位球即时 / E_STATE_PLAY 缓存到下帧的分支 |
| `get_is_owning_ball()` | `:82` | ✅ `return self.ball_owner == team_eid` |
| `change_ball_history` | `:13` `FsProperty` | ✅ 最近 5 帧记录存在 |
| `override_ball_owner` | `:11-12` | ✅ 字段存在 |

**缺口**：`ball_owner` 是单 eid 的 `FsProperty`，**无三态表达**。UNOWNED 期间"`ball_owner` 保留历史值 + 两队 `IsOwningBall()` 均 False"要求必须新增独立的 `ball_possession_state` 字段，而非靠 `ball_owner==eid` 推断。这同时牵动 `get_is_owning_ball()` 的判定源（见 2.4）。

> ⚠️ 注意 `change_ball_owner()` 内 `E_CHANGE_BALL_OWNER` 的 `old_team_eid` 在 `self.ball_owner` 被赋新值**之后**才取，传的是新值。这是真身既有写法，三态改造时需顺带核对该事件的消费者是否依赖 old 值。

### 2.2 预测层 —— `TakeBallManager`

真身路径：`Engine/Sources/External/framecore/external/ai/take_ball_manager.{h,cpp}`
> 该 .cpp 为 UTF-8-BOM，常规读取报编码错，需 grep 取内容。

`_update_ball_owner()`（`take_ball_manager.cpp:333`）逻辑与 manifest 描述**逐行吻合**：

```
触发：dribbling_id == EID_EMPTY && (NoDribbing || Passing)
  ├─ frame_0==0 && frame_1==0          → return（子条件 A：双方无 taker）
  ├─ 双方都有 taker
  │    fast_frame - cur_frame > DOUBLE_SWITCH_BALL_TIME → return（太远不给）
  │    frame 差 > TIME_DIFF_THRESHOLD   → 快方 win_taker（否则子条件 B：势均力敌）
  └─ 单方 taker
       tar_frame - cur_frame < SINGLE_SWITCH_BALL_TIME → win_taker（否则子条件 D：太远）
  防抖：judge_eid 变 → 重置 last_judge_frame；
        cur_frame - last_judge_frame < SWITCH_BALL_OWNER_STAY_FRAME → return
  上报：win_taker 且其队无球权 → py_change_ball_owner(team, eid, is_early=true)
```

**映射结论**：
- 设计的"`has_clear_winner()` 四子条件 A/B/D"在真身里已隐式存在（A=双方无taker；B=帧差≤阈值win_taker为空；D=单方太远）。抽取为独立方法**结构上成立**。
- **子条件 C（球速 > 阈值）在真身完全没有**——`_update_ball_owner` 不读球速，这是**纯新增**逻辑。
- **K 帧门控与现有 `take_frame - cur_frame` 门控同形**。现 `SINGLE/DOUBLE_SWITCH_BALL_TIME=60` 即"剩余帧范围阈值"，把它从"胜者判定的一部分"剥离成"上报输出门控"，再按 `take_ball_info.pass_type` 分化取值即可。`take_ball_info`（`take_ball_manager.h:70`）与 `pass_type` 字段存在，分化配置有落点。

**改造性质**：把"胜者判定 + 上报门控 + 防抖"三件事拆成 `has_clear_winner()`（纯判定）+ K 帧门控（上报）两层。属可控重构，不改预测核心算法。

### 2.4 查询层 —— `FakeTeam.IsOwningBall()`

真身：`FakeTeam.py:544`

```python
if game_mode != STREET and BALL_OWNER_MECH_SWITCH:
    self._is_owning_ball = black_box.get_is_owning_ball(self.eid)
```

### 2.5 战术决策层 —— Situation / TacticTaskManager

真身：`Engine/Sources/External/framecore/external/ai/tactic_tasks/`
设计 §9 引用的四个 Situation **真身全部存在**：
`possession_situation_a` / `overlap_situation_b` / `generic_cross_situation_d` / `generic_finish_situation_e`。

**坐实设计识别的核心问题**：四个 Situation 的 `check_exit_condition()` 首行均为

```cpp
auto dribbler = bb->get_dribbler();
if (dribbler == nullptr) return false;   // 无持球人 → 永不退出
```

（`possession_situation_a.cpp:36` / `overlap_situation_b.cpp:29` / `generic_cross_situation_d.cpp:27` / `generic_finish_situation_e.cpp:29`）

→ UNOWNED（无 dribbler）期间，**所有 Situation 都不退出**，Role 分配与 HR 跑位继续按旧攻防运行。这正是设计要解决的"全队还在前压但球已飞出"现象，问题诊断**真实成立**。

**消费点**：`tactic_task_manager.cpp:233` `m_should_enable = m_team->logic_helper->get_is_owning_ball();`——Situation Bidding 当前**直接消费瞬时球权**。设计要改为消费 `ball_ownership_stable`，重定向点明确。

**缺口**：`BaseSituation`（`base_situation.h:23`）只有 `check_exit_condition()` 纯虚，**无 `is_suspended`/Hold 状态**。设计的"UNOWNED 时 Situation Hold（暂停不销毁）"需在基类新增挂起态，并补"无 dribbler 时强制挂起"逻辑（否则 `return false` 会让它维持在最后状态继续跑 Role）。属净新增。

## 三、与设计假设的偏差（需回写设计的点）

1. **子条件 C（球速）是凭空新增**：设计把 C 列为"从 FIFA 反推的四子条件之一"，但真身 `_update_ball_owner` 完全不涉球速判定。落地时这是一段全新逻辑，需定义球速阈值来源与单位，不能假设"抽取现有逻辑即可"。

2. **NewChaseRule 风险高估**：真身早已 take_frame 选人，设计该风险条目应标注"已满足"，避免投入无谓改造。

3. **三态与 `ball_owner` 的关系**：设计说"UNOWNED 时 ball_owner 保留历史值"，但真身 `get_is_owning_ball` 直接比 `ball_owner==eid`。若仅保留历史值而不引入独立状态字段，则两队中"历史持球方"仍会 `IsOwningBall()==True`，达不到"双 False"。→ **必须**新增独立 `ball_possession_state` 作为判定源，设计需明确这一点（design_v2 已暗示，但实现约束应写死）。

4. **Situation `return false` 的副作用**：设计 §9 已提到，但落地时要注意——单加 Hold 还不够，`check_exit_condition` 在无 dribbler 时返回 false 会让 Situation 永远活着，Hold 必须在 `tick`/Bidding 入口拦截，而非依赖 exit。

## 五、建议落地顺序

按"底层稳定 → 上层消费"自下而上，每层可独立验证：

```
1. 球权层：新增 ball_possession_state 三态 + 改 get_is_owning_ball / IsOwningBall
   验收：调试工具能看到 UNOWNED；UNOWNED 时两队 IsOwningBall 双 False
2. 预测层：_update_ball_owner 拆出 has_clear_winner()；K 帧门控替 SINGLE/DOUBLE_SWITCH_BALL_TIME
   验收：Case 2 进 UNOWNED；长传 has_clear_winner=True 时 Task 不中断
3. 缓冲累积器：BallOwnerManager 新增 N 帧 stable + prev_state + frames_as_them
   验收：反复抢断时 ball_ownership_stable 不翻转
4. 战术层：BaseSituation 加挂起态；TacticTaskManager 消费改 ball_ownership_stable
   验收：反复抢断 Situation 不重竞标；短暂失球拿回不重竞标
5. 执行层：FixTeamHomeRegion 分类处理 + Stay HR；子条件 C 球速逻辑
   验收：Case 3/5/7 非追球人 HR 不切换；GK 豁免正常出击
```

**总判定**：设计与真身代码结构匹配度高，三块净新增（三态原语 / 缓冲累积器 / Situation 挂起）边界清晰、互不阻塞，预测层为同形重构。可进入实现阶段。
