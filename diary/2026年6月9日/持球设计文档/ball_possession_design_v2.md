## 一、现状问题

### 1.1 玩家看到了什么，感受到了什么

当前的球权系统存在两类表现问题，来自同一个根源的不同侧面：

**问题一：无主球期间，攻防状态不响应**

球权争夺期间——传球被拦截、铲球弹球、解围飞行中——玩家会看到一个割裂的场景：

**追球的球员在争球，但场上其他球员还在按"我们拥有球权"的节奏行动。**

进攻球员继续前压，HR 点位还在进攻位置，进攻战术 Task 仍在运行——此刻球根本不属于任何人，谁能拿到还是未知数。

如果对手拿到球，前压的球员直接变成防守漏洞，整个阵型需要从错误的位置开始重新收缩。这个过程玩家能清楚地看到：前场多出几名球员，身后突然出现了空间，但没有任何一个操作能阻止这件事发生。

**问题二：逻辑与表现不一致，攻防切换先于视觉表现发生**

与问题一相反的另一个极端：在直塞和传球被断的场景下，`TakeBallManager` 一旦预测出明确的 take winner，球权逻辑立即切换——此时抢断动画甚至还没有开始播放，视觉上球仍在飞行中。

结果是：**逻辑上刚获得球权的一方（通常是防守转进攻方），此刻场上空档最大**——对手阵型还没来得及调整，而新的进攻方 HR 点位和战术跑位已经在运行。这套战术在视觉上完全没有任何前置铺垫，玩家看到的是"球还没到脚，队友就已经全速冲进攻了"。

这两个问题的体验都指向同一个感受：**AI 行为无法被玩家预读，攻防切换时机和视觉场面对不上**，玩家长期建立不了对 AI 行为的预期，会降低主动发起战术配合的意愿。

### 1.2 问题根因

表面上两个问题方向相反，但往下一层，本质是同一个缺口：

> **球权系统是二元状态（A队 or B队），缺少承载球权交接过程的过渡态及其进入/退出设计。**

没有过渡态，系统处理"球权正在交接"这段时间时只有两条路：
- 继续沿用上一个持球方 → 无主球期间攻防状态不响应（问题一）
- 立即跳到预测出的新持球方 → 预测明确后攻防状态提前切换（问题二）

```
没有中间态
    ├── 无主球判断不清楚 → 卡在原持球方（问题一：切换太晚）
    └── 预测判断清楚了 → 立即跳到新持球方（问题二：切换太早）
                ↓
    两种表现，同一个缺口：
    "球权交接过程"这段时间没有被定义和设计
```

**解法因此也是统一的**：定义 UNOWNED 过渡态（进入条件）+ K 帧出口（退出条件），两者合在一起构成对球权交接过程的完整设计：
- UNOWNED 进入：球权不再属于任何人，阻止系统"卡在原持球方"
- K 帧退出：预测赢方确定后，等到接近触球时机再切换，阻止系统"切换太早"

## 二、设计目的

### 2.1 目标玩家

**全体玩家**。

球权是底层基础设施，玩家在场上只控制一名球员，其余十名（含 GK）的行为由系统决定。球权判定错误引发的问题——攻防状态不稳定、战术执行与玩家看到的场景不一致——是无差别影响所有玩家的系统性问题。玩家在此功能中的角色是**被动受益者与感知者**，他们感知不到系统内部，但能直接感受到"AI 在配合我"还是"AI 在乱跑"。

### 2.2 设计预期

**P0 基础预期**：球权争夺期间，场上的 AI 行为是**连贯且有战术依据**的。追球的球员在争球，等待的球员在维持位置，不再出现"全队还在前压但球已经飞出去无人接"的割裂场景。当球权归属明朗后，攻防状态的切换是干净的，玩家能明显感受到"切换了"而不是"一直在乱"。

**P1 进阶预期**：在球权争夺期间，进攻和防守之间本就存在一次微型博弈——谁拿到球，谁就占据主动。AI 行为的保守与激进倾向，应该能成为这次博弈的一部分变量，而不是完全由系统自行决定、玩家无从感知和影响。

### 2.3 设计目标

| 目标 | 内容 |
|---|---|
| **稳定性目标（P0）** | 建立 UNOWNED 第一类原语，彻底解决无主球阶段 AI 行为的系统性错乱 |
| **体验提升目标（P0）** | 球权切换的时机和过渡更流畅，不出现阵型瞬间跳变 |
| **设计空间目标（P1）** | 开放 UNOWNED 期间的保守/激进行为倾向，为上层调控提供接口 |

> 本设计间接服务于**留存**——消除玩家因"AI 乱跑"产生的挫败感，不作为主要设计驱动。

## 三、设计原则

**不推翻现有球权架构，而是补全缺失的层次：**

1. **在球权层新增 UNOWNED 第一类原语**：不依赖任何行为/动画层枚举，只基于球权语义定义
2. **在球权层和战术层之间插入稳定确认层**：过滤高频切换，让决策层消费稳定信号而非原始信号
3. **前置状态感知替代单纯的 N 帧延迟**：Situation 切换看"球权是怎么变的"，不只看"现在是什么"

**明确不做的事**：
- 不引入球权百分比：球权争夺结果是离散的，百分比适合统计展示，不适合驱动 AI 决策，会让球员行为在两种状态间模糊犹豫
- 不照搬 FIFA 的 Layer1/Layer2 连续累积器：我们的系统是**离散事件驱动**的（kick/pass/hit 等关键帧事件），不需要连续采样信号的平滑层
- 不让 Task 层感知 `ControlStage`：`ControlStage` 是行为/动画层的概念，永远不应穿透到球权层或 Task 层

## 四、整体架构

```
┌─────────────────────────────────────────────────────────────────┐
│  [感知 / 预测层]                                                   │
│                                                                  │
│  ┌─ TakeBallManager（预测驱动）                       【已有】   │
│  │   逐帧预测 take_frame，判断哪方更快拿到球                       │
│  │   K 帧门控（新增）：has_clear_winner + take_frame ≤ K         │
│  │   → 满足时上报 py_change_ball_owner()              【新增】   │
│  │                                                              │
│  │   负责场景：球在无主状态（传球被拦截弹球 / 解围飞行中 /          │
│  │             射门扑出 / 头球争顶等），预测谁先拿到球             │
│  │                                                              │
│  └─ BallOwnerManager（事件驱动）                      【已有】   │
│      监听表现层动画事件（E_TAKE_BALL / E_KICK / E_PASS 等）       │
│      事件触发时直接更新 ball_owner，无需预测，无需 K 帧门控         │
│                                                                  │
│      负责场景：球权通过确认动作转移（正常接球控球 / 铲断成功等）      │
│      = 预测无法给出明确结论时，由动画事件兜底确认                   │
│      = 对预测层的补充，两者合力覆盖全部球权变化场景                  │
│                                                                  │
└──────────────────────────────┬──────────────────────────────────┘
                               │ ball_owner 写入
┌──────────────────────────────▼──────────────────────────────────┐
│  [球权层]                                                         │
│                                                                  │

│                                                                  │
│  ┌ HR 跑位：可直接读取 ball_owner 响应（平滑过渡）    【已有】    │

│  │  再决定是否需要额外平滑处理，或完全依赖 UNOWNED 期间 Stay HR    │
│  └ 战术决策：不直接消费 ball_owner → 必须经过缓冲累积器            │
│                                                                  │
└──────────────────────────────┬──────────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────────┐
│  [缓冲累积器]                                         【新增】   │
│                                                                  │
│  记录：                                                           │
│    prev_possession_state    — 上一个稳定球权状态                  │
│    frames_in_current_state  — 当前状态持续帧数                    │
│    frames_as_them           — 对方连续持球帧数                    │
│                                                                  │
│  判定：                                                           │
│    frames_in_current_state >= N → ball_ownership_stable = True  │
│    + prev_possession_state 判断是否真正易主                       │
│                                                                  │
│  输出：                                                           │
│    "可以触发战术切换" 信号                                         │

│                                                                  │
└──────────────────────────────┬──────────────────────────────────┘
                               │ 稳定信号
┌──────────────────────────────▼──────────────────────────────────┐
│  [战术决策层]                                                      │
│                                                                  │
```

**设计核心**：球权层和战术决策层之间有一个缓冲累积器，而不是直连。HR 跑位响应快，可以随 `ball_owner` 变化平滑调整；Situation 切换代价大，必须等累积器确认状态稳定后才触发。反复抢断时，累积器始终不输出稳定信号，Situation 全程 Hold，AI 不"抽搐"。

## 五、UNOWNED：球权层第一类原语

### 5.1 分层模型

本节说明：为什么 UNOWNED 必须在球权层被显式定义，而不是从下层推断而来。

```
┌──────────────────────────────────────────────────────┐
│  球权层（Ball Ownership Layer）                       │
│                                                      │
│  对外接口：ball_possession_state（三态枚举）           │
│    OWNED_BY_US / OWNED_BY_THEM / UNOWNED             │
│                                                      │
│  UNOWNED 在此层定义，不依赖下层实现细节                 │
└──────────────────────────────────────────────────────┘
             ▲ 向上只暴露三态接口，内部细节不穿透
┌────────────────────────────────────┬─────────────────┐
│  TakeBallManager（预测驱动）        │ BallOwnerManager │
│                                    │  （事件驱动）     │
│  内部：ControlStage / take_frame    │  监听动画事件     │
│  对外：has_clear_winner() + K帧门控 │  直接上报        │
└────────────────────────────────────┴─────────────────┘
             ▲ 向上提供输入
┌──────────────────────────────────────────────────────┐
│  消费层（缓冲累积器 → Situation / Task / HR）          │
│                                                      │
│  ⛔ 永远不感知 ControlStage                           │
│  ✅ 只消费 ball_possession_state 三态                 │
└──────────────────────────────────────────────────────┘
```


### 5.2 UNOWNED 精确定义

```python
@property
def ball_possession_state(self):
    if dribbling_id != EID_EMPTY:
        return OWNED_BY(ball_owner)               # 有持球人，确定
    if take_ball_manager.has_clear_winner():
        return OWNED_BY(predicted_winner)         # 预测明确，提前给
    return UNOWNED                                 # 无主球
```

### 5.3 has_clear_winner() = False 的四个子条件

> 从 FIFA 累积器"不动/慢动"场景反推提炼，完整覆盖所有无主球 Case

| 子条件 | 场景含义 |
|---|---|
| **A** | 双方都没有 taker（弹球后无人追） |
| **B** | 双方都有 taker，帧差 ≤ TIME_DIFF_THRESHOLD（势均力敌） |
| **C** | 球速 > 阈值 **AND**（A 或 B）— 球高速飞行且无明确接球人 |
| **D** | 只有单方 taker 但 take_frame 极大（球离所有人都很远） |

**条件 C 的关键限制**：大力传球给明确接球人时，单方 taker 明确 → `has_clear_winner()=True` → 不进 UNOWNED，进攻 Task 全程不中断。这与真实足球一致：长传/直塞飞行中，进攻球员继续跑战术路线，不等球权确认。

### 5.4 设计预期

**为什么用预测来定义 UNOWNED，而不是用"当前没人持球"这个视觉信号**

"没有人持球"在直觉上很接近无主球的概念，但作为定义有三个问题：

**覆盖不全**：`Passing` 阶段球在飞行，技术上也没人持球，但球权是明确的——接球人正在跑位接应，这不是无主球。"无人持球"不等于"无主球"，前者只是后者的一个子集。

**天然滞后**：等到视觉上能确认没人持球，这个时刻已经是事实发生后的确认。战术层从这里开始响应，就比真实发生晚了一拍——球弹出来了，队友才开始调整站位，AI 看起来"呆"。

**没有调控空间**：视觉事件是二元的，要么发生要么没发生，没有参数可以调。K 帧这个调控维度，只有在"用预测定义 UNOWNED"的框架下才能引出。

**用预测（`has_clear_winner()`）来定义 UNOWNED 的优势**：覆盖了视觉信号漏掉的场景（如 `Passing` 阶段拦截弹球）；通过 K 帧门控，逻辑上比视觉提前介入，但不会提前太多；K 帧本身可配置，给调试和调优留了空间。

逻辑层和表现层是互相依赖的——BallOwnerManager 的事件驱动路径本来就依赖动画事件来确认球权。这里不是要抛弃视觉信号，而是说：**视觉信号适合做事后确认，预测适合做提前判断，两者分工协作，用预测来定义 UNOWNED 是因为它更完整、更主动、有余量。**

## 六、状态机：K 帧定点出口

### 6.1 状态机

```
         dribbling_id == EID_EMPTY  AND  NOT has_clear_winner()
               │
               ▼
  ┌────────────────────────────────────────────┐
  │              UNOWNED 状态                   │
  │                                            │
  │  进入时：                                   │
  │    · ball_possession_state = UNOWNED        │
  │    · ball_owner 保留历史值（记录上一持球方）  │
  │    · IsOwningBall() 两队均返回 False         │
  │    · Situation Bidding Hold                │
  │    · Task 分类处理（见第七章）               │

  │                                            │
  │  持续期间：                                 │
  │    · TakeBallManager 逐帧更新预测           │
  │    · GK 豁免，走独立逻辑                    │
  │                                            │
  └──────────┬──────────────────────────────────┘
             │
             │ 出口条件（K 帧定点触发）：
             │   has_clear_winner() == True
             │   AND  win_taker.take_frame - cur_frame ≤ K
             │
             ▼
  ┌────────────────────────────────────────────┐
  │              OWNED 状态                     │
  │                                            │
  │  切换时：                                   │
  │    · ball_possession_state = OWNED_BY(win)  │
  │    · ball_owner = win 所在队伍               │
  │    · 触发 E_CHANGE_BALL_OWNER               │
  │    · 赢方进入进攻模式，输方进入防守模式        │
  └────────────────────────────────────────────┘
```

### 6.2 时间轴

```
  球弹出（dribbling_id 变空）
  │
  │←─────────── UNOWNED 期间 ──────────→│←── K 帧 ──→│
  │                                     │             │
  │  win_taker 可能反复变化              │             │
  │  Task 按分类规则执行                 │             │
  │                              win 确定 + 剩余 ≤ K  实际触球
  │                              → ball_owner 切换
  │                              → 攻防 Task 激活
```

### 6.3 K 帧的含义与分化

K 帧是 TakeBallManager 向 BallOwnerManager **上报结果的输出门控**，不是预测时机本身的控制。

```
TakeBallManager 内部：
  每帧持续更新预测，has_clear_winner 随时可能变为 True
  → 预测结果在内部保留，不立即上报

上报条件（K 帧门控）：
  has_clear_winner = True
  AND take_frame - cur_frame ≤ K
  → 触发 py_change_ball_owner()，ball_owner 更新

效果：
  不管预测在哪一帧收敛（第 5 帧 or 第 50 帧完成预测）
  ball_owner 的变化时刻始终锚定在"预计触球前 K 帧"
  → 上报时刻统一，消除预测收敛早晚带来的时机不一致
```

| 场景 | 建议 K 值 | 理由 |
|---|---|---|
| 短传（飞行 10~25 帧） | 5~8 帧 | 飞行时间短，K 过大会在出脚前就切换 |
| 常规传球（25~50 帧） | 12~18 帧 | 默认值，平衡响应速度和表现合理性 |
| 长传/直塞（50~120 帧） | 20~30 帧 | 飞行时间长，HR 需要足够的提前量 |
| 无主争球（take_frame 不稳定） | 10~15 帧 | 双方接近势均力敌，避免过早暴露 |

> K 值后续按 `take_ball_info.pass_type` 分化配置，不用单一全局值。

### 6.4 设计预期

K 帧出口的意义是：**球员行为的切换比实际触球提前发生，但不是无限提前**。

这对应了一个真实足球的规律：一名好的球员在球飞向他之前就已经开始调整站位，不是等球到脚下才反应；但他不会在球刚踢出去时就全速冲向禁区，因为他还不确定球是否真的传向自己。K 帧就是这个"判断时机"——足够早，但不过早。

K 值按传球类型分化的原因在于：短传和长传的飞行时间相差 10 倍，如果用同一个 K 值，短传提前量会荒谬地大（还没出脚就全队攻防切换），长传提前量又会不够。分化配置是为了让不同类型的传球都有合理的行为过渡时机。

## 七、UNOWNED 期间行为：分类处理

### 7.1 分类规则

UNOWNED 期间，系统不做统一的"全队中断"或"全队继续"，而是**按球员角色分类处理**：

| 球员类型 | 行为 | 理由 |
|---|---|---|
| **被 NewChaseRule 指派的 taker** | 继续执行 Task（继续冲球） | 直接争球，继续有战术价值 |
| **在预测接球路线上的球员** | 继续执行 Task（继续跑战术路线） | 赢了直接衔接，输了仍在压迫对方 |
| **无 Task / 远端进攻球员** | Stay HR（维持当前 HR 点位，不继续推进） | 避免 UNOWNED 持续过长时过深暴露 |
| **处于危险露出区域的球员** | 向过渡 HR 点位主动收缩 | 超过 MAX_UNOWNED_FRAMES 后触发 |
| **Situation Bidding** | Hold（不重竞标） | 等稳定确认层翻转后才开放 |
| **GK** | 豁免，走独立逻辑 | GK 主动出击扑球，不受分类约束 |

**分类实现原则**：球权层不规定行为。`ball_possession_state` 等全局变量供逻辑决策层读取，行为树节点结合自身角色（是否是 taker、当前位置、前方是否危险）自主决定响应，不需要球权层中央规定"某类 Task 应该怎样"。

### 7.2 时长控制

UNOWNED 是快速过渡态，不是等待态。

```
正常场景（单次争球）：
  MAX_UNOWNED_FRAMES 硬上限（≈ 20 帧，0.33 秒）
  超时 → 强制取当前更优一方为 winner → 退出 UNOWNED

反复抢断（多次争夺）：
  has_clear_winner() 来回翻转，硬上限无法解决
  → 依靠 ball_ownership_stable（N 帧稳定确认）阻断 Situation 抖动
  → Task 不被打断，球员继续按分类规则执行，直到某方连续持球 N 帧
```

### 7.3 设计预期

分类处理的本质是：**不同位置、不同角色的球员，在球权不明的时候，合理的反应本来就不一样。**

直接参与争球的球员继续冲——他最接近球，停下来没有任何战术价值；在接球路线上的球员继续跑——他赢了有位置，输了至少在压迫；远端进攻球员不继续前压——他离球权争夺最远，过早前压一旦失球就是暴露。

这不是设计刻意安排的"保守"，而是每个位置上合理的足球判断，只是过去系统用同一套规则处理所有人，把本该有差异的行为抹平了。

"全队中断进观望"的方案在视觉上会显得突兀——真实足球里不存在全队同时停下来等球权确认的场景。分类处理让每个人做符合自身处境的事，整体上视觉是连贯的。

## 八、全局战术变量（Global Param）整理

项目已有 global_param 机制，这里不新建系统，只整理**战术决策层所需的球权相关变量**，统一由 `BallOwnerManager` 维护写入，供 Situation Bidding 和 Role 执行节点读取。

### 8.1 变量列表

#### 当前状态变量

| 变量 | 类型 | 含义 | 维护者 |
|---|---|---|---|
| `ball_possession_state` | 枚举（三态） | OWNED_BY_US / OWNED_BY_THEM / UNOWNED | BallOwnerManager |
| `ball_ownership_stable` | bool | 当前球权是否已持续 N 帧稳定确认 | BallOwnerManager |
| `has_clear_winner` | bool | 预测层是否有明确赢家 | TakeBallManager |
| `predicted_winner_team` | 队伍 or None | 预测赢家所属队伍 | TakeBallManager |
| `predicted_winner_remaining` | int（帧） | 预测赢家距触球的剩余帧数 | TakeBallManager |

#### 前置状态变量

| 变量 | 类型 | 含义 | 维护者 |
|---|---|---|---|
| `prev_possession_state` | 枚举（三态） | 上一个稳定球权状态（切换前是谁的球） | BallOwnerManager |
| `frames_in_current_state` | int（帧） | 当前 ball_possession_state 已持续帧数 | BallOwnerManager |
| `frames_as_them` | int（帧） | 对方连续持球帧数 | BallOwnerManager |

### 8.2 前置状态 + 持续时间：Situation 切换的判断依据

战术决策层看到"球权属于我方"时，需要区分两种语义完全不同的情况：

| 变化路径 | prev_possession_state | frames_as_them | Situation 响应 |
|---|---|---|---|
| 我方 → UNOWNED → 我方（短暂失去后拿回） | OWNED_BY_US | 0（对方从未真正持球） | 延续当前 Situation，不重竞标 |
| 对方 → 我方（真正的攻守转换） | OWNED_BY_THEM | >= N（确认真正失球过） | 触发 Situation 重竞标 |
| 我方 → UNOWNED（争球中） | OWNED_BY_US | 0 或累积中 | Hold，当前 Situation 暂停不销毁 |
| 我方 → 对方（真正失球） | OWNED_BY_US | 开始累积 → >= N 时确认 | 触发 Situation 重竞标（防守） |

只看 `ball_possession_state` 当前值，前两行无法区分；加上 `prev_possession_state` 和 `frames_as_them`，才能做出语义正确的判断。

### 8.3 频繁争抢：极端场景优先处理

频繁争抢是这套机制需要兜住的极端场景——`ball_owner` 来回跳动，如果 Situation 直接消费原始信号，会跟着每次跳动重竞标，阵型跟物理层同频抖动。

```
反复抢断时：
  ball_owner 来回切换
    → frames_in_current_state 持续被重置
    → ball_ownership_stable 从未翻转
    → Situation 全程 Hold
    → Task 按分类规则继续执行，不被打断

某方连续持球 N 帧：
    → frames_in_current_state >= N
    → ball_ownership_stable 翻转
    → 结合 prev_possession_state + frames_as_them 判断是否真正易主
    → 触发对应的 Situation 响应
```

**极端场景兜住了，普通场景反而不难**：正常攻守转换球权持续时间远大于 N 帧，稳定确认自然通过，不需要额外处理。频繁争抢才是让这套变量体系存在意义的边界场景。

### 8.4 设计预期

这套变量让战术决策层从"感知当前帧是谁的球"升级到"理解球权是怎么变的"。

两者的差别：前者只有一个时间切面，无法区分短暂波动和真正易主；后者有时间延伸——知道上一个状态是什么、当前状态已经持续了多久——才能做出有语义的判断。反复抢断时战术保持稳定，真正的攻守转换时快速响应，这两个预期的实现，都依赖这套时间维度的状态记录。

## 九、参数体系

原 `SWITCH_BALL_OWNER_STAY_FRAME = 6帧` 混做了两件事，现在拆成两个独立参数，分属不同的层次：

```
┌──────────────────────────────────────────────────────────────┐
│                         参数关系图                             │
│                                                              │
│  感知/预测层                                                   │
│    TakeBallManager ──[K 帧门控]──→ ball_owner 写入            │
│    BallOwnerManager ──[事件直接]──→ ball_owner 写入            │
│                                                              │
│                         ↓ ball_owner                        │
│                                                              │
│  球权层                                                       │
│    ├──→ HR 点位（直接读取，平滑响应）                           │
│    └──→ 缓冲累积器                                            │
│                                                              │
│  缓冲累积器（内部参数：N 帧）                                   │
│    frames_in_current_state >= N                              │
│    + prev_possession_state 判断                              │
│         ↓ ball_ownership_stable 翻转                         │
│                                                              │
│  战术决策层（Situation Bidding）                               │
│    只消费 ball_ownership_stable                               │
└──────────────────────────────────────────────────────────────┘
```

| 参数 | 所在层 | 职责 | 消费者 |
|---|---|---|---|
| **K 帧** | 感知/预测层（TakeBallManager 输出门控） | 控制何时上报 ball_owner，保证表现及时性 | ball_owner、HR 点位响应 |
| **N 帧** | 缓冲累积器内部 | 稳定确认，frames_in_current_state >= N 才翻转 stable | Situation Bidding |
| **MAX_UNOWNED_FRAMES** | 球权层内部 | UNOWNED 最长持续时间硬上限，超时强制退出 | 球权层自身 |

### 现有参数改造

| 现有参数 | 处理方式 |
|---|---|
| `SINGLE_SWITCH_BALL_TIME = 60` | 废弃，由 K 帧替代 |
| `DOUBLE_SWITCH_BALL_TIME = 60` | 废弃，由 K 帧替代 |
| `TIME_DIFF_THRESHOLD = 8` | 保留不变 |
| `SWITCH_BALL_OWNER_STAY_FRAME = 6` | 废弃，职责拆入 K 帧（预测层）和 N 帧（缓冲累积器）|

## 十、设计空间：UNOWNED 期间的保守/激进倾向【P1】

> ⚠️ 本章为设计方向草案，具体机制待进一步讨论确认。

### 10.1 背景

UNOWNED 期间，分类处理规则决定了 AI 行为的基准倾向——**但这个倾向本身是可以被调控的**。

"激进"：Task 继续执行的球员更多，冻结的更少 → 球权恢复时攻势更猛，但失球时暴露更深  
"保守"：冻结的球员更多，压迫的更少 → 失球时阵型收得更快，但球权恢复时需要重建推进

这两种倾向没有绝对的好坏，取决于当前局势和玩家的战术意图。

### 10.2 博弈意义

球权争夺本身是一个博弈节点：

```
博弈节点：争球中（UNOWNED）
  打破者：先拿到球的一方
  默认倾向：势均力敌（has_clear_winner = False）
  弱势方缓解口：无法操作改变争球结果（物理决定）
  → 可调控的是：球员在等待结果期间的站位和意图
```

UNOWNED 期间的保守/激进倾向，就是在"无法改变争球结果"的前提下，**玩家能影响的最接近的变量**——通过战术选择或阵容构成，预设 AI 在争球结束后进入的状态。

### 10.3 待讨论的设计问题

| 问题 | 选项 | 说明 |
|---|---|---|
| **调控输入来源** | 战术板保守/激进开关 / tendency 自动决定 / 比分/局势自动触发 | 不同来源对应不同的玩家感知方式 |
| **激进倾向的具体行为差异** | 继续执行 Task 的球员范围扩大？HR 前移？ | 需要定义"激进"的量化边界 |
| **保守倾向的具体行为差异** | 全队 Stay HR？压缩阵型？ | 需要定义"保守"的量化边界 |
| **风险与代价的对称性** | 激进倾向在失球时暴露更深，代价如何量化到 AI 行为 | 保证博弈节点有合理的代价结构 |

## 十三、验收标准

1. Task / HR / InfluenceMap 层代码搜索 `ControlStage`，应**零命中**
2. 在调试工具中，UNOWNED 期间 `ball_possession_state` 有明确的三态标记
3. **Case 验证**：传球被碰未控（Case 3）、直塞被碰弹出（Case 5）、射门扑出弹球（Case 7）期间，非追球人的 HR 点位不切换
4. **Case 验证**：Passing 阶段传球被拦截（Case 2）能正确进入 UNOWNED
5. **Case 验证**：长传/直塞飞行中（has_clear_winner = True），进攻 Task 不中断
6. 反复抢断期间，Situation Bidding 不频繁重竞标（`ball_ownership_stable` 未翻转时保持 Hold）
7. 我方短暂失球后拿回（持续 < N 帧），当前 Situation 延续不重竞标
8. GK 在 UNOWNED 期间能正常出击扑球
