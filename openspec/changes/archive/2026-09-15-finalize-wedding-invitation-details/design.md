## Context

纸张方案已经具备 Open Graph 分享卡片，三个完整方案共享同一日历文件，但页面仍散布姓名、城市与准确时间占位。参见 `proposal.md`；已确认信息完全来自用户本次输入，不需要外部来源验证。

## Goals / Non-Goals

**Goals:**

- 让总览、三个完整方案、分享卡片和日历使用完全一致的正式信息。
- 保持三个主题原有文案语气，并让新增姓名和时间在桌面及移动端不溢出。
- 继续维持现有隐私边界和 `noindex` 设置。

**Non-Goals:**

- 不补写手机号、街道门牌、到场时间、宴席流程或典礼结束时间。
- 不验证酒店商业信息，也不添加地图或第三方服务。
- 不创建或修改文章系列。

## Decisions

### 1. 页面直接写入同一组确认值

四个页面规模很小且当前均为独立静态 HTML，直接替换可见文案与辅助文本比引入 Liquid 数据层更小、更容易在 GitHub Pages 回滚。通过自动扫描确保旧占位没有遗漏。

### 2. 10:58 明确标注为典礼时间

页面统一使用“10:58 典礼”或等价文案，避免宾客误解为必须到场时间。未提供的到场、宴席和结束时间不推断。

### 3. 日历使用 Asia/Shanghai 定时事件且不设置结束时间

日历从全天事件改为带 `TZID=Asia/Shanghai` 的 10:58 开始事件，并内嵌固定 UTC+8 的时区定义。因为结束时间未知，VEVENT 不写 `DTEND` 或时长。

### 4. 分享封面更换文件名

分享封面加入新人、典礼时间和酒店，并改用带日期的新文件名；相比覆盖原 URL，这能减少微信继续使用旧缓存的概率。原分享元数据的 HTTPS 绝对地址、1200×630 尺寸和 JPEG 格式保持不变。

## Risks / Trade-offs

- [较长姓名或酒店名可能在窄屏换行] → 在三个主题的桌面和 390px 移动视口检查首屏与详情区。
- [社交平台仍可能缓存旧分享卡片] → 使用新的封面 URL，并保留可选页面查询参数作为刷新入口。
- [不同日历客户端对无结束时间事件显示不同] → 保留标准 DTSTART 和完整时区定义，不伪造时长。

## Migration Plan

1. 更新页面正文、元数据、辅助文本、分享封面和日历。
2. 扫描旧占位并验证 JPEG、iCalendar、OpenSpec 与页面布局。
3. 推送后检查 GitHub Pages 线上元数据和日历文件；需要回滚时恢复前一提交即可。
