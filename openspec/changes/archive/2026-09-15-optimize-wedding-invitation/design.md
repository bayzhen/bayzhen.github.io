## Context

照片已经以单一 1600px 长边、质量 84 的 WebP 形式接入四个婚礼页面。视觉检查显示布局已稳定，但缩略预览遮罩偏重，部分照片在高像素密度设备上缺少更清晰的候选资源，固定导航滚动后可能遮挡人物。参见 `proposal.md` 的动机和 `wedding-invitation-optimization` 规格的外部行为。

源照片只有约 960–1919px，且人物身份真实性优先于生成式细节。姓名、城市和准确时间尚未提供。

## Goals / Non-Goals

**Goals:**

- 在源分辨率边界内提升边缘清晰度和编码质量，不改变人物身份。
- 让浏览器按显示尺寸和设备像素密度选择照片。
- 解决移动端导航遮挡，并精修三个主题的首屏构图和照片融合度。
- 用当前已确认信息提供可下载的日期提醒。

**Non-Goals:**

- 不进行美颜、换脸、背景替换或服装重绘。
- 不凭照片推断姓名、地点或联系方式。
- 不在未知准确时间时伪造具体开席时间。
- 不引入图片 CDN、第三方 RSVP 或分析服务。

## Decisions

### 1. 生成式增强仅作为候选测试，不直接替换原图

使用身份保真提示生成三张主视觉候选，并逐张与原图对照。当前候选都出现不同程度的面部像素重建，因此不进入仓库；发布版本统一从原 JPEG 做轻度锐化和高质量 WebP 编码。相比直接采用 AI 结果，这一方案的锐度增益较小，但不会改变人物。

### 2. 保留完整版本并增加一个小屏版本

完整版本保持原图像素尺寸并提高编码质量；竖图增加 640px 宽版本，横图增加 800px 宽版本。页面使用宽度描述符 `srcset` 与场景化 `sizes`。两个档位足以覆盖现有布局，并避免过多重复资产。

### 3. 视觉调色由 CSS 完成

图片文件保持统一、自然的颜色；电影、纸张和东方的轻微对比度与饱和度差异放在页面 CSS 中。这样同一照片复用时不需要生成多个调色副本，也便于撤回。

### 4. 移动端导航按滚动方向自动收起

共享脚本只在窄屏且离开页面顶部后检测滚动方向：向下收起，向上显示。键盘焦点进入导航时强制显示，减少无障碍操作风险；桌面行为不变。

### 5. 日历先使用全天事件

新增标准 iCalendar 文件，将 2026-10-06 记录为全天日期，并在描述中注明上午和具体安排私下告知。等准确时间提供后再改为带 `Asia/Shanghai` 时区的定时事件，避免现在写入错误提醒。

### 6. 纸张方案主视觉使用源照片的竖幅比例

纸张方案的首图画框固定为与 1024×1536 源照片一致的 2:3 比例，并在桌面端限制最大宽度。图片使用完整适配而不是继续填满随视口变宽的横向网格：超宽屏会保留更多纸张留白，但不会再牺牲新娘和礼服的完整构图。移动端同样沿用该比例，使不同视口的裁切行为一致。

## Risks / Trade-offs

- [轻度锐化可能放大原 JPEG 噪点] → 使用克制的锐化参数并在桌面和手机实际渲染尺寸检查。
- [提高质量会增加完整图片体积] → 小屏版本配合 `srcset` 抵消移动端流量增长，并继续保留懒加载。
- [自动收起导航可能让入口暂时不可见] → 页面顶部、向上滚动和获得焦点时立即恢复。
- [全天日历不会在上午自动提醒] → 描述明确“上午”，待准确时间确认后再升级为定时事件。
- [限制主视觉宽度会在超宽屏增加留白] → 将留白作为纸张方案的编辑感构图，并优先保留完整人物。

## Migration Plan

1. 在临时目录生成全部 WebP，再验证尺寸、格式和元数据后替换现有网页副本。
2. 更新图片属性、共享脚本、页面样式和日历入口。
3. 运行 OpenSpec 严格校验与 Jekyll 构建，并在桌面和 390px 窄屏检查首屏、中段相册、导航行为和横向溢出。
4. 若锐化或构图效果不理想，可回退到当前九张 WebP 与原有 CSS；原始 JPEG 始终保留在仓库外。
