## Context

婚礼页已有九组照片的小图和高清 WebP：小图总计约 575 KB，高清图总计约 1.6 MB。当前相框缩略图没有 `src`，展开视图在互动时才设置 `srcset`，这能节省流量，但在延迟较高或吞吐不稳定的移动网络下会把等待暴露给访客。

## Goals / Non-Goals

**Goals:**

- 尽早预热全部小图，让花开、星落、相框和最终邀请首先有可立即显示的版本。
- 在不阻塞首屏的情况下预热高清图，并优先处理流程中较早出现的照片。
- 保持现有响应式清晰度选择和加载失败回退。

**Non-Goals:**

- 不把图片转成 Base64 或嵌入 HTML。
- 不引入 Service Worker、离线安装或第三方图片 CDN。
- 不预加载背景音乐，也不改变浏览器自动播放规则。

## Decisions

1. **小图使用文档级预加载提示。** 在样式链接之后声明九个 WebP 小图，主背景使用高优先级，其余使用低优先级。浏览器可以在脚本初始化和互动之前发现请求，并对与页面实际图片相同的 URL 自动去重。
2. **高清图由现有游戏脚本在首屏完成后预热。** 等待 `load`，再通过空闲回调（带超时回退）启动队列，避免与 CSS、脚本和首屏背景竞争最关键的加载时段。
3. **高清队列限制为两个并发请求并按叙事排序。** 花开正面照片优先，其后是直接查看邀请可能使用的背景，再加载星光背面照片；有限并发能避免弱网连接被九张大图同时占满。
4. **使用独立 `Image` 对象预热浏览器 HTTP 缓存。** 对象保存在页面生命周期数组中，成功和失败都推进队列；展示逻辑仍设置原有 `src`/`srcset`，因此缓存可用时命中，不可用时自然重试。
5. **暴露非视觉预热状态用于验证。** 根容器以数据属性标记等待、预热中和完成状态，不增加进度弹窗，也不让访客等待下载完成才能操作。

## Risks / Trade-offs

- [访问者会下载比实际观看更多的图片] → 当前全套高清 WebP 约 1.6 MB，体积可控；使用小图优先和两路后台并发避免首屏突发。
- [预加载提示可能与首屏资源竞争] → 样式链接先声明，非主背景小图使用低优先级，高清图延后到首屏完成后。
- [浏览器不支持空闲回调或 fetch priority] → 提供定时器回退；不支持优先级提示时仍能正常预加载。
- [网络失败导致状态无法完成] → `load` 与 `error` 都视为一次队列结算，失败不影响游戏，后续真实图片元素可重新请求。

## Migration Plan

加入预加载提示和脚本队列，更新静态资源版本号后部署。通过无交互网络日志验证小图和高清图均已提前请求；若发现首屏明显变慢，可独立回退预加载提交，不影响照片或游戏数据。
