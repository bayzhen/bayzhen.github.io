## Context

现有站点由 GitHub Pages 兼容的 Jekyll 构建，既有共享布局页面，也有完全独立的静态 HTML 页面。婚礼候选页需要拥有与技术博客完全不同的视觉表达，同时在正式照片、姓名、城市和准确时间尚未提供时可独立预览。参见 `proposal.md` 的动机与 `specs/wedding-invitation-concepts/spec.md` 的可观察行为。

## Goals / Non-Goals

**Goals:**

- 让用户通过三个完整长页而非孤立色板比较视觉方向。
- 用一致的信息层次和照片占位结构控制比较变量。
- 让后续替换姓名、城市、精确时间和真实照片保持低成本。
- 在微信等移动端内置浏览器中仍具备良好的首屏与滚动体验。

**Non-Goals:**

- 本阶段不确定最终方案，也不合并为正式邀请函。
- 不提供 RSVP、数据库、访问密码、地图导航、音乐或联系方式。
- 不修改主站导航，不向现有博客样式表添加婚礼专属规则。

## Decisions

### 独立专题目录与独立样式

采用 `wedding/index.html` 作为候选入口，三个方向分别位于 `wedding/cinematic/`、`wedding/editorial/` 和 `wedding/oriental/`。资源置于 `wedding/assets/`，每个方向拥有自己的样式表，并共享极少量基础重置和进入动画脚本。

这样可以避免技术博客的导航、深色模式变量和通用文章规则污染邀请函。备选方案是新增 Jekyll layout，但它会把一次性专题抽象成全站能力，当前没有收益。

### 无外部字体与图片依赖

候选阶段使用系统自带的衬线、无衬线、宋体和楷体字族，并通过 CSS 色块、边框和排版形成照片占位。这样本地和 GitHub Pages 预览一致，也不会因为第三方字体或临时图库不可用而破坏页面。

正式照片到位后，仅替换占位容器内容并补充响应式图片资源。若最终需要特定字体，可在选定方案后单独评估自托管字体及授权。

### 三种美学语言

- 电影感：深墨色背景、暖白文字、超大日期、宽银幕构图和克制的金色强调。
- 法式纸张感：暖象牙纸色、酒红强调、编辑式不对称网格、细线与植物感曲线。
- 东方雅致：宣纸灰、黛黑、朱砂红、竖排点题、留白和印章式元素。

三个方向使用相同内容模块，但允许重新排序和重新命名章节，使视觉节奏真正区别，而不是只换颜色。

### 渐进增强的滚动动画

基础 HTML 默认可见；JavaScript 只在脚本成功执行后启用轻量滚动揭示。`prefers-reduced-motion` 会关闭动画。该策略保证脚本失败、低性能设备和辅助技术仍能访问全部内容。

### 隐私与生命周期

所有候选页设置 `noindex, nofollow`，主站不链接婚礼页。具体会场与联系方式不进入仓库。页面结束发布时可删除或替换专题，但接受 Git 历史与搜索缓存可能保留已公开姓名、日期和城市这一静态托管特性。

## Risks / Trade-offs

- [系统字体在不同设备上的字形略有差异] → 使用宽容的字体栈并避免依赖精确字宽的布局。
- [无真实照片时难以完全判断气质] → 三套方案使用相同尺寸的明确照片预留位，选定方向后再做一次真实素材适配。
- [三个完整页面带来重复内容] → 候选阶段优先保证视觉自由；最终只保留选中的一个版本，避免长期维护成本。
- [`noindex` 不能提供真正隐私] → 页面只放用户已同意公开的信息，具体会场和联系方式始终线下发送。

## Migration Plan

1. 新增候选入口、共享资源和三个方案目录，不修改现有路由。
2. 使用现有 Jekyll 配置构建并验证四个路径。
3. 用户选定方向并提供照片后，在后续变更中将其完善为 `/wedding/` 正式页。
4. 婚礼结束后删除专题或替换为感谢页；回滚时只需移除 `wedding/` 目录。
